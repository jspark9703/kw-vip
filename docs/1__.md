# 1번 장애물·패널 인식 할 일 (전용휘)

2026-11-23 작성. 11-17 회의에서 정한 세 서브태스크 중 제가 맡은 1번(장애물 및 패널 확인)에서 할 일만 정리했습니다.
기준은 과제 공지 요구사항입니다. 코드 구조는 박준수 님 개발 가이드(11-16 기준)를 따랐습니다. 서버 코드는 아직 직접 열어 보지 않았으므로 새 파일 이름은 제안입니다.

## 0. 요약

카메라 영상에서 패널, 버튼, 장애물을 찾아 각각의 3D 위치를 2번(박준수)과 3번(빈서현, 윤태영)에게 넘깁니다.
- 찾는 방법: YOLO 세그멘테이션(segmentation, 물체마다 화소 단위 윤곽을 내는 검출)
- 3D 위치: 찾은 윤곽 안의 depth 값으로 계산
- 층 번호: 지금 장면의 색 규칙(1층 빨강, 2층 초록, 3층 파랑)을 그대로 씀
- 쓰는 시점: 움직이기 전 head 카메라 한 번, 움직이는 동안 손목 카메라 매 프레임

막혔는지 판단과 우회, 팔 충돌 설정은 2번이 하고 누르기와 눌렸는지 판단은 3번이 합니다.

## 1. 공지 요구사항과 1번의 관계

| 공지 내용 | 1번이 할 것 |
|---|---|
| 상황 인식, 명령 해석, 동작 생성, 물리 실행, 결과 확인을 하나의 시스템으로 연결(과제 목표) | 이 중 상황 인식을 맡음. 카메라 영상에서 패널·버튼·장애물 위치를 구해 넘김. 시뮬레이터 정답 좌표 방식(`ik_gt`)은 비교 기준으로만 둠 |
| 장면에 없는 버튼을 누르라는 명령에는 움직이지 않거나 수행 불가를 알림 | 장면에서 찾은 버튼 목록을 넘김. 명령의 층이 목록에 없으면 기존 `reject` 경로로 감. 장애물 때문에 누를 수 없을 때의 판단은 2번 |
| 성공·실패 사례 영상 | 영상에 검출한 윤곽과 장애물 상자를 겹쳐 그려 무엇을 보고 움직였는지 보이게 함 |
| 반복 평가로 수치화 | 검출 정확도, 3D 위치 오차, 처리 시간을 고정 시드로 측정 |
| 최종 추론은 각자 컴퓨터에서 | 학습한 모델이 노트북 CPU 에서 돌아야 함. 팀원 노트북마다 처리 시간을 잼 |

공지에 버튼 숫자를 읽으라는 조건은 없습니다. 그래서 숫자 읽기(OCR)는 5장의 선택 작업으로 뺐습니다.

| 1 | 서버 접속(준수 님께 비밀번호 요청), clone, `perception/camera.py`·`sim/scene.py` 읽기 | `tests/check_camera.py` 실행 |

| 4 | 학습 데이터 자동 생성(`perception/seg_gen.py`). MuJoCo segmentation 영상에서 윤곽을 뽑아 YOLO 라벨로 저장 | 라벨을 영상에 겹쳐 눈으로 확인 |

| 7 | `pipeline.py` 에 연결하고 영상에 윤곽·상자 표시 | `run_demo.py` 로 장애물 있는 장면 영상 1개 |
| 8 | 평가 시드 고정 후 4장 지표 측정 | 결과 표 |
| 9 | 모델을 ONNX 로 바꿔 노트북 CPU 처리 시간 측정 | 팀원 노트북별 프레임당 ms |

4·5번은 제가 DOFBOT 과제(분리수거 로봇팔)에서 MuJoCo 라벨로 YOLO seg 를 학습할 때 쓴 스크립트를 고쳐 씁니다.

### 2.1 학습 데이터에서 바꾸는 것

학습 장면을 다양하게 만들어 특정 장면에만 맞춰지지 않게 합니다(domain randomization).

| 바꾸는 것 | 범위(초안) |
|---|---|
| 패널 위치·각도 | 가이드 9.2 요인 A~C 범위보다 조금 넓게 |
| 버튼 배치 | 순서, 가로·세로, 간격 6~10cm |
| 장애물 | 상자·원기둥·구, 크기 2~15cm, 색 무작위, 0~3개 |
| 조명 | 밝기·방향 무작위 |
| 카메라 | head 카메라, 손목 카메라(팔 관절각 무작위) |

학습 장면은 개발 시드(0~999)로만 만들고 평가 시드(10000 이상)는 쓰지 않습니다(가이드 3.2).
로봇 팔과 휠체어는 배경으로 학습합니다. 팔이 카메라에 찍혀도 장애물로 잡지 않게 하려는 것입니다.

### 2.2 3D 위치 계산

| 대상 | 방법 |
|---|---|
| 패널 | 패널 윤곽 안 depth 점들로 평면을 맞춰(RANSAC) 중심·법선·크기 계산 |
| 버튼 | 버튼 윤곽 안 depth 점들의 중앙값이 위치, 법선은 패널 법선 |
| 장애물 | 장애물 윤곽 안 depth 점들로 중심과 상자(AABB, 축에 나란한 직육면체) 계산 |

YOLO 는 학습에서 본 모양만 잘 잡습니다. 그래서 패널보다 휠체어 쪽에 있는 depth 점 중 어느 윤곽에도 속하지 않는 점이 뭉쳐 있으면 그것도 장애물로 넘깁니다. 장애물을 놓치는 쪽이 없는 장애물을 넘기는 쪽보다 위험하기 때문입니다.

## 3. 넘기는 데이터

카메라 프레임 한 장마다 아래 형식의 데이터(JSON) 하나를 냅니다. 좌표는 world 좌표(m)입니다.

```json
{
  "camera": "head_rgb | wrist_rgb",
  "panel": {"center": [x, y, z], "normal": [nx, ny, nz], "size_m": [w, h], "score": 0.97},
  "buttons": [{"id": 4, "floor": 3, "pos": [x, y, z], "normal": [..], "score": 0.95}],
  "obstacles": [{"id": 7, "center": [..], "aabb_min": [..], "aabb_max": [..],
                 "found_by": "yolo | depth"}],
  "timing_ms": 0.0
}
```

- `id`: 프레임이 바뀌어도 같은 물체에 같은 번호가 붙습니다(Ultralytics 에 들어 있는 ByteTrack 추적).
- `found_by`: YOLO 가 찾은 장애물인지 YOLO 가 놓쳐 depth 로 찾은 장애물인지 구분합니다.
- 장애물 부분은 2번이 쓰기 편한 형식으로 바꿀 수 있습니다(6장).
- 3번이 쓰는 실행 인터페이스(`execute(task, sim)`)는 바꾸지 않습니다. 목표 버튼 위치·법선을 지금 `perception/camera.py` 결과가 들어가는 자리에 넣습니다.

## 7. 미리 확인해 둔 MuJoCo 동작

제 노트북(MuJoCo 4.0.1)에서 작은 시험 장면으로 확인했습니다. 서버 버전에서도 한 번 다시 돌리겠습니다.

| 항목 | 결과 |
|---|---|
| `Renderer.enable_segmentation_rendering()` | int32 (H, W, 2). 채널 0 은 물체 id, 채널 1 은 물체 종류(geom 이면 5), 배경은 -1. 학습 라벨을 여기서 뽑음 |
| `Renderer.enable_depth_rendering()` | float32 (H, W), 단위 m, 카메라 광축 방향 거리. 배경은 약 69.7 같은 큰 값이라 최대 거리로 잘라야 함 |
| 렌더 시간 | 160×120 depth 한 장 1.2ms |

depth 화소를 world 좌표로 바꾸는 코드입니다. 상자 앞면 x = 0.5700, 패널 앞면 x = 0.9800 으로 정답과 같게 나왔습니다.

```python
def depth_to_world(model, data, cam, depth, max_m=2.0):
    cid = mujoco.mj_name2id(model, mujoco.mjtObj.mjOBJ_CAMERA, cam)
    H, W = depth.shape
    f = (H / 2) / np.tan(np.deg2rad(model.cam_fovy[cid]) / 2)
    v, u = np.mgrid[0:H, 0:W]
    ok = depth < max_m
    x = (u + 0.5 - W / 2) / f * depth
    y = -(v + 0.5 - H / 2) / f * depth
    pc = np.stack([x, y, -depth], -1)[ok]          # MuJoCo 카메라: -z 가 시선, +y 가 위
    R = data.cam_xmat[cid].reshape(3, 3); t = data.cam_xpos[cid]
    return pc @ R.T + t, ok
```
