확정된 선택과 시스템 구성
버튼 3개를 누르는 IK 기준선을 먼저 완성하고, 같은 조건에서 ACT 정책과 비교한 뒤 큐브로 확장합니다. 텍스트는 규칙과 로컬 LLM이 작업 JSON으로 바꾸고, 실행부(IK 또는 ACT)는 그 JSON만 보고 움직입니다.

명령 하나가 처리되는 흐름:
1.  입력: "2층 눌러줘"
2.  해석 (nlu/): 규칙으로 부정·대기 표현을 먼저 걸러내고, 나머지는 Ollama LLM이 JSON으로 바꿈
3.  검증 (nlu/validate.py): 장면에 있는 버튼(1~3층)인지 확인하고, 없으면 거절하며, 층수가 빠지면 되물음
4.  목표 위치 (perception/): 처음에는 site 좌표를 쓰고, 나중에 카메라 검출로 교체
5.  실행 (control/ 또는 policy/): IK 상태 기계나 ACT가 ctrl을 내보내고 MuJoCo가 물리 스텝을 진행
6.  판정 (eval/): 목표 버튼 변위 ≥ 10mm이고 다른 버튼은 3mm 미만이면 성공. 로그와 영상을 저장
이 구조에서는 실행부만 교체하면 IK와 ACT를 같은 시드로 비교할 수 있고, 그 차이가 "기준선 대비 개선량"이 됩니다.

setfacl -R -m u:vipuser:rwX /home/jspark/kw-vip
setfacl -R -d -m u:vipuser:rwX,u:jspark:rwX /home/jspark/kw-vip
# 확인 (vipuser로): touch /home/jspark/kw-vip/.perm_test && rm /home/jspark/kw-vip/.perm_test
setfacl을 쓸 수 없다면 서버 관리자에게 공용 그룹을 만들어 달라고 요청합니다. 두 계정을 같은 그룹에 넣고 폴더에 chmod g+rwXs를 걸면 됩니다.

단계별 구현 프로세스
일정을 유동적으로 가져가는 대신, 각 단계의 통과 조건을 만족해야 다음 단계로 넘어갑니다. Phase 3이 끝나면 발표에 필요한 최소 결과가 확보되고, Phase 4~6은 그 위에 쌓는 확장입니다. Phase 1과 2는 동시에 진행할 수 있습니다.
1.  Phase 0 — 환경과 장면 (① 주도, 전원 참여)
    ◦ 폴더 권한 설정, vla-shell 점검, Git 저장소와 폴더 구조 만들기
    ◦ make_scene_v2.py로 models/scene_v2.xml 생성
    ◦ sim/scene.py에 make_scene(seed, condition) 작성: 패널 위치를 model.body_pos로 바꾸고 목표 층을 뽑음. 초기 상태는 시드만으로 재현돼야 함
    ◦ 통과 조건: 서버에서 3개 층 모두 10mm 이상 눌림. mp4 녹화가 됨
2.  Phase 1 — IK 실행부 (②)
    ◦ control/ik.py: press_tip 기준 6D DLS IK. 다중 초기값으로 풀고, 이전 해에서 이어서 풀어 손목이 뛰지 않게 함. IK는 복사본에서만 계산
    ◦ control/press_fsm.py: 그리퍼 닫기 → 접근(5cm 앞) → 단계적 전진(16mm) → 판정 → 후퇴. 단계별 타임아웃과 실패 유형 태깅
    ◦ 인터페이스: execute(task, sim) -> {success, peak_mm, other_mm, fail_type, t_task}
    ◦ sim/recorder.py: head_rgb + 보기 좋은 자유 카메라 화면에 명령·해석 결과·상태·변위(mm)를 텍스트로 겹쳐 mp4로 저장 (선택 10번)
    ◦ 통과 조건: 학습 범위 무작위 30회에서 28회 이상 성공
3.  Phase 2 — 명령 해석 (③)
    ◦ nlu/schema.py: {intent: press|wait|reject|clarify, floor, reason}
    ◦ nlu/rules.py: 층수 추출(숫자·한글 숫자 "일/이/삼층"), 누르기 동사, 부정·대기 표현("하지 마", "누르지 말고", "기다려", "멈춰")
    ◦ nlu/llm_ollama.py: Ollama의 JSON 출력 모드와 few-shot 프롬프트. 모델은 1.5B~3B급 instruct를 후보로 두고 한국어 테스트셋으로 고름. 호출마다 지연 시간을 기록
    ◦ nlu/validate.py: 규칙의 부정·대기 판정을 항상 우선 적용. 장면에 없는 층이면 reject, 층수가 없으면 clarify("몇 층을 눌러 드릴까요?")
    ◦ 테스트셋: 팀원이 각자 10문장씩 40문장을 작성(재표현·금지·불가능·모호 골고루). 평가용 5문장은 여기에 넣지 않음
    ◦ 통과 조건: 40문장 중 규칙만으로·규칙+LLM으로 각각 몇 개를 맞추는지 표로 기록. 금지·불가능 문장에서 움직이는 경우는 0개
4.  Phase 3 — 통합과 기준선 평가 (④ 주도, 전원)
    ◦ run_demo.py: 텍스트 → 해석 → 검증 → 실행 → 결과 출력과 녹화
    ◦ eval/run_eval.py: eval_config.yaml의 고정 시드로 기본 10회, 변화 10회, 명령 5회를 실행하고 시도별 JSON과 mp4를 저장
    ◦ 통과 조건: IK 기준선 결과표 첫 버전 완성. 이 시점에서 발표 최소 요건이 충족됩니다
5.  Phase 4 — ACT 정책 (④ + ②): 다음 섹션에서 자세히 설명. 통과 조건은 같은 20회를 ACT로 실행해 IK와 비교한 표
6.  Phase 5 — 카메라 인식 (③)
    ◦ head_rgb에서 버튼 색으로 검출(HSV 임계값)하고, depth 렌더링과 카메라 내부 파라미터(fovy 72)로 3D 위치를 복원
    ◦ 기본 자세에서는 팔이 버튼을 가리므로, 관찰할 때 팔을 시야 밖으로 빼는 자세를 정하거나 카메라 각도를 조정
    ◦ perception/의 출력만 교체해 같은 20회를 재평가하고, 위치 오차(mm)도 기록
7.  Phase 6 — 큐브 확장 (여유가 있을 때)
    ◦ 집기 상태 기계: 열기 → 위 10cm → 하강 → 닫기 → 5cm 이상 들기 → place_zone 위 → 내려놓기 → 열기 → 후퇴
    ◦ 명령 스키마에 pick_place를 추가하고, 같은 방식으로 20회 평가
    ◦ 큐브 새 위치에서 수직 파지가 되는지 Phase 0에서 먼저 확인
8.  Phase 7 — 노트북 이식과 최종 (전원)
    ◦ 각자 노트북에 clone, Ollama 모델·ACT 체크포인트 복사. 네트워크를 끊고 run_demo.py 실행
    ◦ 노트북에서 추론 지연(LLM 1회, ACT 1스텝)을 측정하고, 발표용 성공·실패 영상을 녹화
ACT 학습 파이프라인 (Phase 4)
ACT는 텍스트를 직접 입력받지 않습니다. 명령 해석기가 나타낸 목표 층을 원-핫 벡터로 바꿔 관측에 붙여 넣습니다. 이렇게 하면 정책 하나로 3개 층을 처리하고, "텍스트가 동작에 어떻게 영향을 주는가"를 한 문장으로 설명할 수 있습니다.

LeRobot 데이터셋 형식 (outputs/datasets/press_v1)
학습
4070 Ti에서 LeRobot ACT. 배치 크기·chunk 길이·스텝 수는 작게 시작해 늘림. 설치된 LeRobot 버전의 학습 명령과 설정 이름을 먼저 확인
실행
고정 시간(예: 10초) 동안 정책을 돌리고, 판정은 IK와 같은 코드(목표 ≥ 10mm, 다른 버튼 < 3mm)
진행 순서:
1.  policy/gen_demos.py로 작은 데이터셋(층당 10개)을 만들어 형식과 재생을 먼저 확인
2.  작은 데이터셋에 과적합시켜 학습 코드와 실행 코드가 끝까지 도는지 확인(학습 장면에서 성공해야 정상)
3.  전체 데이터셋으로 본 학습을 하고, 체크포인트마다 개발용 시드 30회로 성공률을 재서 고름(평가 시드 사용 금지)
4.  고른 체크포인트로 평가 20회를 실행하고 IK와 비교
5.  노트북으로 체크포인트를 복사해 CPU/GPU 추론 지연을 측정
발표에 공개해야 하는 것(학습 중에 바로 기록): 에피소드 수, 데이터 생성 방식, 관측과 행동 형식, 학습 설정과 시간, 체크포인트 크기, 사전학습 가중치 출처.
예상되는 위험과 대응:
• 인접한 버튼을 누름: 버튼 간격이 8cm라 ACT 위치 오차가 크면 오동작이 납니다. 실패 유형을 "오동작"으로 따로 집계합니다
• 눌림 깊이 부족: 데모가 16mm까지 누르기 때문에 여유는 있지만, 부족하면 마지막 누르기 구간을 IK가 맡는 하이브리드를 비교군으로 둠
• 변화 조건에서 성능 하락: 예상되는 결과이며, 그 자체가 일반화 격차 분석의 재료입니다. 학습 범위를 넓혔을 때와 비교하면 개선 방향을 제시할 수 있습니다
평가·영상·발표 산출물
같은 고정 시드 20회와 명령 5회를 실행부별(IK, ACT, 카메라 인식 포함)로 돌려 하나의 비교표를 만드는 것이 최종 결과물입니다. 시드와 조건은 eval_config.yaml에 평가 전에 고정하고, 실패한 시도도 빼지 않습니다.
